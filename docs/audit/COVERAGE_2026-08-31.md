### From the auth lane (2026-08-31, later session) — found, NOT fixed

- **The pending trap (highest).** `ProtectedRoute.tsx` evaluates
  `approval_status === 'pending'` before the Big-7 profile gate, so a user who
  confirms their email and then abandons `/complete-profile` is bounced to
  `/account-pending` from every route. That screen says "Our team is reviewing
  your credentials", shows "Final admin review — Waiting", and promises "under
  2 hours" — while `complete-signup` auto-approves and **there is no review
  step at all**. It offers no link to `/complete-profile`. The account then sits
  until `cleanup-abandoned-accounts` deletes it at day 30. Prod shows 0 pending
  profiles today, but that is *consistent with* victims having already been
  deleted, not evidence there were none.
- **`/account-pending`'s SLA is unbacked.** `REVIEW_SLA = "under 2 hours"` +
  "Overnight signups clear next morning" are delivered by one deduped admin
  notification (dedupe window 24h — 12× the promise). No cron, no deadline
  column, no escalation, no telemetry measuring `approved_at − created_at`.
- **Brute-force protection is client-side only.** Login's 5-strike lockout lives
  in `safeStorage`. Measured: `localStorage.clear()` + reload resets it and the
  next attempt reaches the network. Correct for its stated threat model (a
  stolen phone driving the UI); whether GoTrue's own rate limit backs it is a
  dashboard setting not readable from this repo.
- **`/reset-password` has no loading state.** `ready` starts false, so the
  "use the reset link from your email" copy paints immediately on a valid link
  before `getSession()`/the hash parse resolves — and if the exchange fails the
  user is left on that wrong message permanently.
- **A successful password change is silent.** `ResetPassword.handleSubmit`
  shows a toast on failure and *nothing* on success — it just navigates to
  `/dashboard` after 800ms. The adjacent comment ("without making the user stare
  at a toast") describes a toast that no longer exists.
- **`/reset-password` is not in the AASA `paths`**, so on iOS a reset link opens

  still holds the old session. Deliberate or not, it is undocumented.

  lands on `/dashboard`. Intentional per the comments, but the plumbing is dead.
- **A dead session presents as "you're still signed in."** `ProtectedRoute`'s

## 4. Method notes worth keeping

Traps that cost real time today; all are now in `CLAUDE.md`:

1. `position: fixed` is **not** viewport-relative here — `backdrop-filter` on every
   frosted surface creates a containing block.
2. A Tailwind variant over a hand-written class compiles to **nothing**; an inline
   `background` shorthand silently overrides `background-image`. **Assert gloss by
   reading the computed style, never the class name.**
3. `parsecheck` does not resolve symbols — a missing import can bind a DOM global.
4. The Supabase CLI is linked to **staging** while `.env` is **prod**.
5. `supabase migration list --linked` therefore reports the wrong project — this is
   where the false "36 pending migrations" figure came from.
6. Service-role bypasses RLS. **Query as a real signed-in user or the gate will
   look like it works when it does not.**
7. PGlite runs migrations locally without Docker; apply 3× to prove replay-safety.
8. A guard that has never failed is not evidence. Reintroduce the defect, watch it
   fail, revert — and include a control proving the guard *reaches* the code.

### 7.2 Offline — L3, writes driven with the network actually cut

`OfflineBanner` is **globally mounted and live**, not a stale flag: with a real
`context.setOffline(true)` it appears within ~1s reading *"You're offline.
Showing the last data we have."*, and it clears on reconnect. Copy is honest —
it deliberately does not promise a retry queue, and there is none.

Behaviour per flow, each driven and reconciled against prod rows:

| Flow | Fully offline | Flaky (link up, request aborts mid-flight) |
|---|---|---|
| **Send a message** (`sendHandlers.ts`, bare `await`) | `requireOnline()` blocks it; sonner toast *"You're offline. Try again when you're back."* at +400ms; typed text retained in the composer; **0 prod rows**. Correct. | Optimistic bubble → `sendStatus: "failed"` + tap-to-retry. Correct. |
| **Save a job** (`useSaveJob`, `useMutation`) | **DEFECT — see below** | Fires, fails, **rolls back** (label stays "Save job"), toast *"Couldn't save that job right now / Tap retry to try again. / Retry"* visible from +300ms; **0 prod rows**. Correct. |
| Lifecycle transitions, post a job, save profile, reviews, disputes, offer accept/decline | All bare `await` + `try/catch` + toast, several with explicit optimistic rollback (`useLifecycleHandlers.ts:292/331`, `JobTracking.tsx:913/936`). Read, not driven. | — |

**HIGH — `queryClient` sets no `mutations.networkMode`, so every `useMutation`
pauses silently offline.** `src/lib/queryClient.ts:21-48` has **no `mutations`
key at all**; `networkMode` appears zero times in the repo. The default is
`'online'`, which *pauses* a mutation when `onlineManager` reports offline:
`onMutate` runs (optimistic UI applied), `mutationFn` never runs, **`onError`
never runs** — so no rollback, no toast. Driven on the save-a-job path:

```
+300ms  aria-label="Unsave job"  sonnerToasts=[]  netSinceTap=0  (banner only)
+700ms  aria-label="Unsave job"  sonnerToasts=[]  netSinceTap=0
prod saved_jobs 0 -> 0   (while offline)
prod saved_jobs 0 -> 1   (on reconnect — it resumed)
```

So the UI says saved, **zero requests are made**, the row does not exist, and
the user is given no action-specific feedback. It is recovered *only* if the app
stays alive to reconnect. Driven again with the app closed before reconnect:
**prod `saved_jobs` before 0 → after close+reconnect 0. The write is silently
lost.** There is no outbox anywhere in `src/` (`outbox`/`pendingWrites`/
`offlineQueue` → zero hits); TanStack's in-memory paused-mutation resume is the
only replay and it does not survive a process restart.

Same shape, unguarded, on: `PayItForward.tsx:257` `donateMutation` (**money**),
`StrSettings.tsx:67/:180`, `PetProfiles.tsx:80`. `useApplyFlow.ts`'s
`applyMutation` is equally naked and is saved only by a UI-layer `online` guard
in `ApplyBody.tsx:147-165` — one refactor away from a silent apply, with no test.

Single highest-leverage fix: add
`mutations: { networkMode: "always", retry: 0 }` to `queryClient.ts`. Every
paused-and-silent mutation then behaves like the bare `await` paths that
already work.

Also found, not fixed:
- `requireOnline()` (`src/lib/requireOnline.ts:21`) reads **`navigator.onLine`
  only** and never consults `@capacitor/network`, even though `useOnlineStatus`

  `useOnlineStatus.ts:46-48` documents as untrustworthy. 4 call sites.
- **No reachability probe** against Supabase anywhere — captive portal, expired
  session and a Supabase outage all read as "online".
- **Realtime never resubscribes.** 11 bare `.subscribe()` sites; only
  `useActivityData.ts:645` observes status, and it reports to Sentry rather than
  telling the user. Its own comment: *"a failed channel is a SILENT failure."*
- `OfflineBanner` is `lazy()` (`App.tsx:23,573`) — on a cold offline boot its
  chunk can fail to load and the banner never appears.
- **Zero tests exercise a write while offline.** The two e2e offline tests
  (`zz-runtime-probe.spec.ts:578,646`) dispatch a synthetic `window` `offline`
  event and only assert banner/copy. That is why 1–3 above are invisible to CI.

### 8.3 Finding 3, worked out: what day 2 and day 3 actually do

The cron is `0 6 * * *` (migration `20260823170000`) and `FUND_LEAD_DAYS = 3`, so
a visit on date **D** is inside `d > today && d <= today+3` on exactly three
runs — D−3, D−2, D−1 — and out of it on D itself. Consecutive runs are 24 hours
apart to the second; a Stripe idempotency key lives 24 hours. Therefore:

| | key state | what Stripe does with an identical request |
|---|---|---|
| two overlapping runs, same day | live | **replays** the one PaymentIntent |
| next day's run | expired | **mints a new charge** |

So the key never protected the window it appears to protect. Day 2 and day 3 are
safe only because the pre-flight `existing` read sees the row day 1 created — and
that read's error was being dropped. The chain that produced a double charge:

1. day 2, `existing` read faults transiently → empty set → "no visit yet";
2. charge with the same key, now expired → **a second, real PaymentIntent**;
3. `jobs_one_visit_per_series_date` rejects the insert → `23505`;
4. old branch: *"both runs hold the SAME PaymentIntent, no refund"* — false on
   day 2 — so the duplicate is never refunded, and the run answers `200 ok:true`.

Driven day-by-day in the harness: day 1 issues one charge keyed
`recurring-visit:series-1:2026-09-04`; **days 2 and 3 send Stripe nothing at
all**; day 4 does not even consider the visit. The key is deliberately left
stable (same-day protection is worth having); cross-day correctness now rests on
the read plus the 23505 disambiguator, which is where it always actually was.

### 8.3b A SIXTH finding, from the review pass: "declined" ≠ "no answer"

Not on the handover list. Found by the adversarial correctness reviewer while
checking whether any cross-day double-charge path survived finding 3's fix — and
one did. It is the path the unique index **cannot** catch:

1. `paymentIntents.create` reaches Stripe, the charge succeeds, and the
   **response is lost** (connection reset, socket timeout, 5xx);
2. the old code treated any throw as a decline: no job row, and the poster is
   told their payment failed;
3. tomorrow's run finds `alreadyThere` legitimately empty — there really is no
   row — and charges again on a key that expired overnight, so it is a
   genuinely new PaymentIntent;
4. **that** insert succeeds. No `23505`, because the first intent never got a
   row to collide with. Two real charges, one visit, and nothing anywhere is
   looking for the orphan.

Fixed in two layers. First, the charge is retried once on the **same
idempotency key** — which is what the key is for: while it is live Stripe
replays the original outcome, so a lost response costs one extra request and
nothing else, and a request that never arrived is simply made. Second, an error
is now classified: `StripeCardError` and `StripeInvalidRequestError` are
*answers* (no money moved → an ordinary decline, 200, no page), while anything
else — including a raw throw with no `type` — is **no answer**, and when even
the retry gives none the run records a defect and posts a critical alert naming
the idempotency key and the amount, so a human can check Stripe *before* the
next run charges over the top of it. The poster and helper are still told the
date is not booked; that fact is true either way.

### 8.3 The retention policy — three buckets, and why each row is in its bucket

**ERASE** — identifies the person, belongs to nobody else. Profile PII, ID
documents, avatars, portfolio and credential files, chat attachments, messages
they *sent*, notifications, push tokens, preferences, unfunded/unapplied-to
jobs they posted, notification logs, login history, saved jobs, fraud flags,
their referral code and unspent referral credit.

**ANONYMISE** — somebody else's record, or a record the law requires. Sever the
identity, keep the row:
- `reviews.reviewer_id` CASCADE → **SET NULL**. A review is part of the
  *reviewee's* public record; for a Helpr their rating is their livelihood.
  `reviews.reviewee_id` deliberately **keeps CASCADE** — a review *about* a
  person who is gone is a judgment about an identified individual and serves no
  reader.
- `payout_transfers.helper_id` RESTRICT → **SET NULL** + a new
  `helper_redacted_at` stamp. Statutory retention; `amount_cents`,
  `platform_fee_cents`, `job_id` and `stripe_transfer_id` stay authoritative and
  reconcile against Stripe. The stamp is what makes "redacted" distinguishable
  from "never written".
- `payout_transfers.job_id` **keeps RESTRICT** — that guard is correct. What
  made it a blocker was `jobs.customer_id` being CASCADE; fixing that to SET
  NULL removes the conflict without weakening the ledger.
- `jobs.customer_id/helper_id`, `disputes.opener_id/decided_by`,
  `pif_credits.donor_id/recipient_id`, `skill_endorsements.endorser_id`,
  `group_job_helpers.helper_id`, `referrals.referrer_id`,
  `referral_credits.referred_user_id`, and every actor/pointer column → SET NULL.

**RETAIN untouched** — `admin_audit_log` (compliance trail), messages the
counterparty *wrote* (`messages.receiver_id` stays dangling on purpose: the
one-sided thread is the honest representation of "the other person left"), and
every money column above.
