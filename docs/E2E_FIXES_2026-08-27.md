## F-1 (P0, trust/identity) — an applicant's profile opens a different person

**This is the one that matters. Fix it first.**

### Steps
1. Sign in as Account A on the simulator.
2. My Posts → Needs You → expand "Weed the front flower beds".
3. Applicants (2) → tap the first applicant.

### Expected
The profile of `6bdc1f67-ae1f-46a0-8edf-4035629a6147` — **Audit Helper**, the
account that actually applied.

### Actual
The profile of **Eli Thibodeaux** (`11111111-1111-1111-1111-111111111104`), an
unrelated account: his name, avatar, "Metairie", his bio ("Painter and
assembly. IKEA furniture welcome."), *and fabricated relationship claims* —
"You've worked together 10 times", "0% cancel rate · 0/11 jobs",
"7 Posted / 1 Completed". No console error. No failed request.

This is the poster's vetting screen — where someone decides whether to let a
stranger into their home — and it shows the wrong human being's identity and
trust record.

### Root cause (verified against live prod)

`public.get_safe_profiles`:

```sql
WHERE (p.user_id = ANY(user_ids) OR p.id = ANY(user_ids))
```

The `OR p.id = ANY(...)` arm matches the profile row's **primary key** as well
as the user id. Eli Thibodeaux's `profiles.id` *is*
`6bdc1f67-ae1f-46a0-8edf-4035629a6147`, which is Audit Helper's `user_id`.

Live probe — asked for one id, got a different user back:

```
get_safe_profiles(['6bdc1f67-ae1f-46a0-8edf-4035629a6147'])
  -> [{ user_id: 11111111-1111-1111-1111-111111111104, full_name: "Eli Thibodeaux" }]
```

Asked for two ids, got one right row, one wrong row, and the requested row
missing entirely:

```
get_safe_profiles(['6bdc1f67-...', 'f2b3ad99-...'])
  -> f2b3ad99-...  "Audit Weblane"      (correct)
  -> 11111111-...104 "Eli Thibodeaux"   (NEVER REQUESTED)
  -> 6bdc1f67-...    MISSING
```

(Audit Helper is additionally `ban_status = 'temp_banned'`, which is why his own
row is filtered out. That part is correct behaviour — do not "fix" it.)

### Why it reaches the screen

`src/pages/userProfile/useUserProfileData.ts:83`

```ts
const profileRes = await supabase.rpc("get_safe_profiles", { user_ids: [userId!] });
let prof = (profileRes.error ? null : profileRes.data?.[0] ?? null) as any;
```

`data?.[0]` is taken with **no check that the returned `user_id` matches the id
that was asked for**.

Note the applicants *list* does re-match on `user_id`
(`useApplicantsState.ts`, `profilesRes.data?.find(p => p.user_id === app.helper_id)`),
which is why the list degraded to the generic fallback name "Helpr" instead of
showing Eli there. The list masked the bug rather than surfacing it — that
masking is itself worth removing.

### Severity, stated honestly

The collision exists here because seed data reused one uuid across the two
columns. A *chance* collision in production is vanishingly unlikely. It is still
P0 because:

- the function **silently returns the wrong identity rather than nothing**, and
- `profile_id` is part of this very RPC's output, so the ids that trigger the
  `p.id` arm are ids the app itself hands to clients.

### What to do

1. Decide whether lookup-by-`profiles.id` is a real requirement. Grep all 19
   call sites (`grep -rl get_safe_profiles src/`). If nothing passes a
   `profiles.id`, **drop the `OR p.id = ANY(user_ids)` arm** in a migration.
   If some call site does rely on it, split it into a separate, explicitly
   named function so the two key spaces can never be confused.
2. Independently, make every single-row call site defensive:
   `useUserProfileData.ts` must assert `prof.user_id === userId` and fall
   through to its self-select / not-found path otherwise. A row that does not
   match what was asked for is a bug, not a result.
3. Migration rules apply: `npm run migration:new -- <slug>`, never hand-type a
   timestamp, keep it replay-safe, and ship the PGRST202 fallback if any client
   code starts calling a brand-new RPC.
4. **Verify by operating the app**, not by reading the diff: repeat the three
   steps above and confirm the correct helper (or an honest "profile
   unavailable" for the banned account) appears. Screenshot it.

## F-2 (P2, correctness) — My Posts crashes to the error boundary on first open

### Steps
1. Cold-launch the app signed in as Account A.
2. Tap the My Posts / Activity tab (clipboard icon) for the first time.

### Expected
The My Posts list.

### Actual
The error boundary: "This page hit a problem. We've logged it. Try again or
head back home." Tapping **Try Again** recovers fully and the list renders
correctly (Needs You 2 / Scheduled 3 / Waiting 0 / Done 2 — which reconciles
exactly to Account A's 7 posted jobs).

### Status — needs characterisation before it can be fixed
I could **not** reproduce it on subsequent tab switches within the same session
(Home → Activity, twice, both clean). So it is first-load-only, and the repro
almost certainly needs a **cold relaunch**, not a tab switch.

### What to do
1. Reproduce deterministically: `launch` the app fresh N times and tap Activity
   first thing each time. Establish the actual hit rate before changing code.
2. The error boundary says "We've logged it" — find the logged error. Check
   `report()` output / the Supabase logs for the stack. Do not guess at the
   cause from reading components.
3. Prime suspect worth checking first: a first-render race where the applicants
   or posted-jobs loader runs before the session/profile is hydrated. But
   **confirm from the logged stack** — do not fix on this hunch.

## F-3 (P3, visual layout) — Photo Proof Before/After buttons overlap

### Steps
1. Account A → My Jobs → Scheduled → scroll to "Clean out a garage"
   (`5eed0828-0002-4000-8000-000000000005`, arrived + working).
2. Look at the Photo Proof card.

### Expected
Two side-by-side buttons, "Before Photos" and "After Photos", each inside its
own half of the two-column grid.

### Actual
"Before Photos" is clipped underneath "After Photos", and "After Photos"
overflows the card's right edge. Stable across repeated screenshots — not a
mid-scroll artifact.

### Root cause
`src/components/PhotoProof.tsx:338` lays the columns out as
`grid grid-cols-2 gap-3`. Grid tracks default to `minmax(auto, 1fr)`, so their
min-width is the child's intrinsic width — and the child is a
`whitespace-nowrap` Button (`src/components/ui/button.tsx:52`). At 402pt the
button's intrinsic width exceeds its fair share, so both tracks blow past the
container.

### What to do
This is visual, so **the owner's standing rule applies: confirm the intended
look before editing.** The mechanical fix is `min-w-0` on the two column divs
(letting the tracks shrink) plus a decision about what the button does when it
no longer fits — truncate, wrap, or shorten the label to "Before" / "After".
That last part is a design call, not a guess to make silently.

Verify at 402pt in the simulator **and** at 375px in the browser, with a
screenshot of each.

## Not bugs — do not "fix" these

Each of these looked wrong during the run and was cleared by checking the
database. Re-deriving them costs an hour each.

- **Browse showing only one job is CORRECT.** Only 2 of 10 open jobs are
  funded, and `open_jobs_browse` deliberately requires
  `payment_status IN ('escrow','payout_pending','released')` — documented at
  length in `20260831010000_active_dispute_flag_and_unfunded_job_visibility.sql`
  (F-1 in that file). Excluding Account A's own post, exactly 1 job should
  render. Every filter was confirmed at its neutral default first.
- **"Payment auto-releasing to you" is not an empty promise.** The
  `auto-release-payment` cron is active (`5,35 * * * *`) and its query does
  match the waiting job. It hasn't fired only because the seed row has no
  `stripe_payment_intent_id`. Seed artifact.
- **The second applicant really is named "Audit Weblane".** `f2b3ad99` is a
  distinct account that happens to share Account A's display name. The poster
  is not seeing themself.
- **Audit Helper being withheld is correct.** That account is
  `ban_status = 'temp_banned'`, and `get_safe_profiles` is supposed to withhold
  banned rows.
