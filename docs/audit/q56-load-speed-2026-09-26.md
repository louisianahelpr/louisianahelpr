# Q56 morning report: what makes the app load slowly, and what to change (measured 2026-09-26)

Dated record. Every number below was measured on 2026-09-26 by the cloud session on
branch `cloud/open-audits`, and says where it came from. Nothing here is a live count.

## How it was measured, and what was NOT measured

- **Build:** this commit's production `vite build`, served by `vite preview` on
  127.0.0.1, talking to the real prod backend (the same method `lighthouse.yml` and
  `a11y-webkit-prod.yml` use since 2026-09-14). The deployed site (louisianahelpr.com,
  its CDN and its TTFB) could **not** be reached from the container: the egress policy
  denies that host. So TTFB and CDN caching of the web app itself are not measured here.
- **Lighthouse 12**, the exact `.lighthouserc.json` settings (mobile, simulated throttling).
- **Playwright Chromium**, Lighthouse's "Slow 4G" (150 ms RTT, 1.6 Mbps) + 4x CPU,
  375x812 and 1440x900, median of 3 cold loads per route.
- **WebKit: not measured** (the container has no WebKit build, and installing one is
  not allowed here).
- **Signed-in dashboard in a browser: not measured.** The test-account variables
  exist in this container but are empty. Used instead: prod edge logs (24 h to
  2026-09-26 04:00Z) and `pg_stat_statements`.

## Ranked list (biggest expected gain first)

1. **Paint the public pages before the JS boots (prerender `/`, `/login`, `/signup`, `/browse` shell).**
   Costs now: LCP 5.8-6.6 s, of which 5.4-5.9 s is "render delay" (the LCP text exists
   only after React renders); the screen is blank page background until FCP (~3.4 s),
   because the boot loader is empty by owner decision (Q651).
   Change: build-time prerender of the static first screen of those routes into their
   HTML (the build already snapshots an OG shell, `scripts/generated/og-shell.js`), then
   hydrate. Expected gain: LCP close to FCP-of-HTML, roughly -3 to -4 s on Slow 4G.
   Budget: the new Lighthouse LCP/FCP error budgets (below) are lowered in the same commit.
   Owner decision first: it is an architecture change to the landing (whose hero is LOCKED
   in look, not in how it is delivered). Filed as Q652.
2. **Cut Realtime's database cost.** Costs now: 4,103 s of DB time, the single largest
   consumer by 4.6x; this is the class of load that starved the DB on 2026-09-22 (Q53).
   Change: count the `postgres_changes` subscriptions per signed-in page and the tables in
   the `supabase_realtime` publication; move per-user fan-out (badges, notifications) to
   one channel per user (the `userRealtimeBus` pattern) and drop tables nothing listens to
   from the publication. Expected gain: proportional to subscriptions removed; not
   estimated until counted. Filed as Q653 (with a budget: a two-way inventory of
   publication tables vs subscribers).
3. **Take ~140 KiB of unused JS off the boot path.** Costs now: Lighthouse reports
   138-146 KiB unused on every public route; 294 KB gz boot graph. Change: find what the
   boot graph pulls that the first screen does not run (app-shared is 134 KB gz on its own).
   Budget: exists (`scripts/perf/critical-path-budget.json`, checked by bundle-size.yml;
   lower it with the change). Filed as Q654.
4. **Cache versioned images for a year.** Costs now: every avatar view revalidates after
   1 h (and on every view for the 38 `no-cache` objects); 6,873 avatar GETs in 24 h, and
   Storage's object lookup is the #3 DB statement. Change: upload with
   `cacheControl: "31536000"` (URLs are already versioned by `?t=`), and re-put the 38
   `no-cache` objects. Expected gain: most repeat avatar loads leave the network and the DB.
   Filed as Q655 (guard: every storage `.upload(` passes `cacheControl`).
5. **The `applications` + `jobs` embed (893 s, 86k calls).** Already the subject of Q53's
   hot-query work; the dashboard polling named in this item's text is gone (no
   `refetchInterval` on those reads; badge counts are one shared store per user,
   src/hooks/useActivityBadgeCounts.ts). Next step is an index/plan check of the embed's
   filter. Filed inside Q653's DB pass.
6. **Two slow housekeeping queries.** `pg_timezone_names` (426 ms mean, 278 calls) has one
   caller to find and cache; `check_db_saturation()` (261 ms, every ~2 min) is the monitor
   itself. Small in total (118 s / 209 s); listed so they are not rediscovered.

Fonts (78 KB, font-display passes) and CSS (33 KB) are not where the time goes.
