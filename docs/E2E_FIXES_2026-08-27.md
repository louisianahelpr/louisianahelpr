## F-1 (P0, trust/identity) — an applicant's profile opens a different person

**This is the one that matters. Fix it first.**

### Steps
1. Sign in as Account A on the simulator.
2. My Posts → Needs You → expand "Weed the front flower beds".
3. Applicants (2) → tap the first applicant.

### Expected
The profile of `6bdc1f67-ae1f-46a0-8edf-4035629a6147` — **Audit Helper**, the
account that actually applied.

### Actual
The profile of **Eli Thibodeaux** (`11111111-1111-1111-1111-111111111104`), an
unrelated account: his name, avatar, "Metairie", his bio ("Painter and
assembly. IKEA furniture welcome."), *and fabricated relationship claims* —
"You've worked together 10 times", "0% cancel rate · 0/11 jobs",
"7 Posted / 1 Completed". No console error. No failed request.

This is the poster's vetting screen — where someone decides whether to let a
stranger into their home — and it shows the wrong human being's identity and
trust record.

### Root cause (verified against live prod)

`public.get_safe_profiles`:

```sql
WHERE (p.user_id = ANY(user_ids) OR p.id = ANY(user_ids))
```

The `OR p.id = ANY(...)` arm matches the profile row's **primary key** as well
as the user id. Eli Thibodeaux's `profiles.id` *is*
`6bdc1f67-ae1f-46a0-8edf-4035629a6147`, which is Audit Helper's `user_id`.

Live probe — asked for one id, got a different user back:

```
get_safe_profiles(['6bdc1f67-ae1f-46a0-8edf-4035629a6147'])
  -> [{ user_id: 11111111-1111-1111-1111-111111111104, full_name: "Eli Thibodeaux" }]
```

Asked for two ids, got one right row, one wrong row, and the requested row
missing entirely:

```
get_safe_profiles(['6bdc1f67-...', 'f2b3ad99-...'])
  -> f2b3ad99-...  "Audit Weblane"      (correct)
  -> 11111111-...104 "Eli Thibodeaux"   (NEVER REQUESTED)
  -> 6bdc1f67-...    MISSING
```

(Audit Helper is additionally `ban_status = 'temp_banned'`, which is why his own
row is filtered out. That part is correct behaviour — do not "fix" it.)

### Why it reaches the screen

`src/pages/userProfile/useUserProfileData.ts:83`

```ts
const profileRes = await supabase.rpc("get_safe_profiles", { user_ids: [userId!] });
let prof = (profileRes.error ? null : profileRes.data?.[0] ?? null) as any;
```

`data?.[0]` is taken with **no check that the returned `user_id` matches the id
that was asked for**.

Note the applicants *list* does re-match on `user_id`
(`useApplicantsState.ts`, `profilesRes.data?.find(p => p.user_id === app.helper_id)`),
which is why the list degraded to the generic fallback name "Helpr" instead of
showing Eli there. The list masked the bug rather than surfacing it — that
masking is itself worth removing.

### Severity, stated honestly

The collision exists here because seed data reused one uuid across the two
columns. A *chance* collision in production is vanishingly unlikely. It is still
P0 because:

- the function **silently returns the wrong identity rather than nothing**, and
- `profile_id` is part of this very RPC's output, so the ids that trigger the
  `p.id` arm are ids the app itself hands to clients.

### What to do

**Read this before touching the RPC.** The `OR p.id = ANY(user_ids)` arm is
**deliberate and load-bearing** — do NOT drop it. It was added by
`supabase/migrations/20260817230000_get_safe_profiles_resolve_by_profile_id.sql`
because `public.messages.sender_id` / `receiver_id` carry **no foreign key**,
and prod genuinely stores `profiles.id` values where an auth id belongs (that
migration names a real thread on job `a5eed000-...-008` holding Marie Hebert's
profile id). `profiles` RLS only admits `auth.uid() = user_id`, so this
SECURITY DEFINER function is the only lever those callers have. Remove the arm
and the Messages inbox regresses to rendering those threads as "User".

So the defect is not "it accepts two key spaces". The defect is that it accepts
two key spaces **and then returns the match without telling the caller which
key matched**, so a caller asking by `user_id` cannot tell a `user_id` hit from
an unrelated `p.id` hit. Fix that, not the arm:

1. **Client guard (do this first — it alone stops the P0 render).**
   `src/pages/userProfile/useUserProfileData.ts:83` takes `data?.[0]` blind.
   Prefer the row whose `user_id` equals the requested id; only fall back to a
   `profile_id` match when no `user_id` row came back. A row matching on
   neither is a bug, not a result — drop it and take the not-found path.
   The RPC already returns `profile_id`, so no schema change is needed for this.
2. **Then make the ambiguity impossible to ignore server-side.** Options worth
   weighing (pick one, do not do all three): return a `matched_on` column
   (`'user_id'` | `'profile_id'`) so callers can disambiguate; or order results
   so `user_id` matches sort first; or split into two explicitly named
   functions and migrate the profile-id callers over. Whichever you pick, the
   Messages path that motivated the original migration must keep working —
   verify it, don't assume.
3. Audit the other 13 call sites for the same blind-index pattern. Most build a
   lookup map keyed on `user_id` (which is why they degraded to the "Helpr"
   fallback instead of showing the wrong person) — those are safe but are
   *silently dropping* rows, which is what hid this bug. Consider logging when
   a requested id comes back unmatched.
4. Migration rules apply: `npm run migration:new -- <slug>`, never hand-type a
   timestamp, keep it replay-safe, ship the PGRST202 fallback if client code
   starts calling a brand-new RPC.
5. **Verify by operating the app**, not by reading the diff: repeat the three
   steps above and confirm the correct helper (or an honest "profile
   unavailable" for the banned account) appears. Then open Messages and confirm
   no thread regressed to "User". Screenshot both.

### Root cause

`grid grid-cols-2 gap-3`. Grid tracks default to `minmax(auto, 1fr)`, so their

`whitespace-nowrap` Button (`src/components/ui/button.tsx:52`). At 402pt the
button's intrinsic width exceeds its fair share, so both tracks blow past the
container.

### What to do
**Characterise before fixing — do not fix on the static-CSS theory alone.**
Reproduce it deliberately: scroll the card into view on a cold load and
screenshot the *first* paint, then force a re-layout and screenshot again. If
it only ever breaks on first paint, the fix is about layout stability (font
loading / measurement), not about the grid rule.

This is visual, so **the owner's standing rule applies: confirm the intended
look before editing.** The mechanical fix is `min-w-0` on the two column divs
(letting the tracks shrink) plus a decision about what the button does when it
no longer fits — truncate, wrap, or shorten the label to "Before" / "After".
That last part is a design call, not a guess to make silently.

Verify at 402pt in the simulator **and** at 375px in the browser, with a
screenshot of each.

## F-6 (P1, privacy/trust) — job-match notifications leak the exact street address

A helper who has **not** been awarded a job receives its **full street address**
in a push/in-app notification. This defeats an address-masking control the
product implements deliberately everywhere else, and contradicts a promise the
product makes to the poster in writing.

### Steps
1. Sign in as Account A on the simulator.
2. Tap the bell (Notifications) → scroll to the "THIS WEEK" group.
3. Read any "Match for you" row.

### Expected
The city only — "Lafayette, LA" — matching what Browse shows for the same job.

### Actual
`Match for you — LIFECYCLE — 01 escrow fund in 123 Main St, Lafayette, LA 70503 · $120. Tap to review and apply.`

The house number and street are printed to a helper who has not been picked.

### Evidence chain (all verified against live prod)

The masking control exists and is deliberate — `open_jobs_browse`:

```sql
CASE WHEN offered_to_helper_id = auth.uid() THEN location
     ELSE mask_job_location(location) END AS location
```

and it really does strip the street:

```
mask_job_location('123 Main St, Lafayette, LA 70503') -> 'Lafayette, LA'
mask_job_location('73 Rue Fontaine, Lafayette, LA 70508') -> 'Lafayette, LA'
```

The product promises exactly this to the poster —
`src/components/postjob/LogisticsSection.tsx:239`:
"Only your city is shown until you pick a Helpr."

But both matcher edge functions read the **raw `jobs` table** with the service
role, bypassing the view and its mask, and interpolate `location` verbatim:

- `supabase/functions/instant-job-match/index.ts:53`
  `.from("jobs").select("id, title, category, location, budget, customer_id, is_urgent")`
  → line 230: ``message: `${job.title} in ${job.location} · $${job.budget}. Tap to review and apply.` ``
- `supabase/functions/daily-match-digest/index.ts:43`
  `.select("id, user_id, job_id, created_at, jobs(id, title, category, location, budget)")`
  → line 83: same interpolation.

`jobs.location` genuinely holds full street addresses in prod — e.g.
`73 Rue Fontaine, Lafayette, LA 70508` and
`1408 Rue Beauregard, Delcambre, LA 70528`.

### Why this is worse than it looks
The leak is **broadcast**, not one-to-one: a match notification goes to every
helper matching the job's category/skills, so one posted job can push a
private home address to many strangers at once. It also persists — the address
is baked into `notifications.message` at insert time, so it stays readable in
the notification history even after the job is gone (the rows I found reference
jobs that no longer exist).

### What to do
1. Apply the mask at the source in both edge functions. Prefer calling the
   existing `mask_job_location()` rather than reimplementing the parse — one
   masking rule, one place. Do not merely change the message template in a way
   that still passes the raw string around.
2. Check every other **service-role** reader of `jobs.location` for the same
   bypass. The view protects clients under RLS; edge functions are exactly the
   code path that escapes it, so grep those first:
   `grep -rn "location" supabase/functions/ | grep -i job`.
3. Decide, deliberately, what the awarded helper sees and when the full address
   is released — that is the one legitimate unmasking, and the view already
   encodes the rule (`offered_to_helper_id = auth.uid()`). Match it.
4. Backfill is a judgment call for the owner: existing `notifications.message`
   rows still contain leaked addresses. Sanitising them is a data fix, not a
   code fix — raise it, do not silently rewrite user-visible history.
5. Verify by operating the app: trigger a match notification for a job whose
   `location` has a street number, and confirm the rendered row shows city only.

## F-4 (P1, correctness) — the hired helper cannot message the poster

Found on the second pass. This one is unambiguous and mechanical: the client is
strictly more restrictive than the backend, and the backend already models the
rule correctly.

### Steps
1. Account A → My Jobs → Scheduled → "Hang six pictures"
   (`5eed0828-0002-4000-8000-000000000002`; A is `helper_id`, status `accepted`,
   `payment_status = 'escrow'`, scheduled Sun Aug 30 2:00 PM, $66).
2. Tap the card's **Message** button — a primary action the card itself offers.

### Expected
A usable composer. A is the *hired helper* on a funded, scheduled job.

### Actual
The thread opens with the header correctly reading **ACCEPTED**, and then the
composer is **replaced by a padlocked notice**:

> "Your application's in. The poster will reach out here if they're interested —
> you'll be able to reply as soon as they do."

There is no input at all. The helper cannot contact the poster — not to ask
where to park, not to say they are running late — until the poster messages
first. On the day of a job that is an operational failure, and the copy
misstates the state: the application is not "in", it was accepted days ago.

### Root cause — client only

`src/components/messages/ChatView.tsx:225-227`

```ts
const isApplicant = !activeConvo.viewerIsPoster;
const posterHasMessaged = messages.some((m) => m.sender_id !== userId);
const composerLocked = isApplicant && !posterHasMessaged;
```

The poster-first rule ("stops posters being flooded by applicants") is aimed at
*pending* applicants, but the condition is simply "not the poster", so it also
catches the **assigned helper on an accepted job**.

### The backend disagrees — and the backend is right

`public.can_message_in_job` (the `WITH CHECK` on the `Users can send messages`
INSERT policy) permits three cases:

1. the job's poster (`j.customer_id = _sender`);
2. **"the helper this job is offered to, or already assigned to"** —
   `j.offered_to_helper_id = _sender OR j.helper_id = _sender`;
3. the poster messaged this sender first.

Account A satisfies case 2, so **the server would accept the insert**. The
client omits case 2 entirely and blocks it.

The comment above the lock in `ChatComposer.tsx:78` asserts "The backend RLS
policy enforces the same rule server-side." **That claim is false** — fix the
comment along with the code.

### Fix
`composerLocked` must also be false when the viewer is the job's assigned or
offered helper, mirroring `can_message_in_job` case 2. `activeConvo` needs to
carry that fact (or derive it from the job row it already loads). Keep the lock
for genuine pending applicants — that rule is real and server-enforced.
